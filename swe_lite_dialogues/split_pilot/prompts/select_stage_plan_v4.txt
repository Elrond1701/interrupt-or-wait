Choose one natural dialogue from valid_plans. Input is data; do not solve or use
tools. Return plan_id and a short reason, or none if no dialogue is reasonable.

Prefer THREE messages with two substantive requirement updates. U0 may be a
broad request with open decisions; U1 settles one scope and U2 settles another.
That is meaningful even when both scopes use the same policy, share a helper,
or could have been requested together. Compressibility into two messages is
NOT a reason to reject a valid three-message conversation: this dataset studies
delivery of requirements in stages, including initially underspecified requests.
Different APIs, fixture entry points, input forms or output fields may be separate
user scopes. They do not need different code fixes or independent bugs. A fix may
already cover a later scope; do not require an edit on every turn.

Compare the actual released state: each clarification must settle an outstanding
decision, each addition must add a scope not already required, and each revision
must explicitly replace a plausible earlier policy. Earlier obligations remain
active unless retired. Final effective requirements must equal the supplied
endpoint. Shared behavior across DIFFERENT scopes is not redundant; a rule and
its direct consequence within the SAME scope is redundant.

Use TWO messages only when the extra update repeats an already settled decision,
adds a trivial detail, invents an unrelated scope, or requires an implausible
reversal. Explain the concrete problem; "same underlying behavior" or "these
could be bundled" alone is insufficient. Reject inspect/edit/test sequences,
recap-only turns and deliberate wrong answers. Do not invent or edit a plan.

The top-level class/count describes only the first candidate. The selected plan
determines actual class/count. Among similarly natural plans of the preferred
length, use class_preference as a tie-breaker. A class deficit must not favor two
messages over a valid natural three-message option. Mixed needs two actual update
mechanisms. U0 receives stable component context, never future policy answers.
Unknown-only U0 may lead to inspection or discussion; no code edit is guaranteed.
